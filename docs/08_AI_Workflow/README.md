# 개발 작업 전달 지침

## 공통 지침

현재 팀 합의 전 설계안은 `docs/02_Architecture/README.md`다. 실제 코드 수정에 들어가기 전에 확정된 패턴·State 계약을 따른다. 각 작업자는 담당 파일과 focused 테스트 범위부터 공유한다. 통합 파일을 임의로 동시에 수정하지 않는다.

새 기능은 실패 사례를 먼저 만든 뒤 최소 구현한다. LLM/검색 호출 mock 테스트와 실제 최종 실행을 구분한다. 결과에는 변경 파일, 테스트 명령·exit code, 미확인 항목, 다음 통합 의존성을 남긴다. API key와 비밀값은 출력하거나 commit하지 않는다.

## Supervisor/Graph 작업

`graph.py`의 고정 Fan-out을 상태 기반 Supervisor로 전환한다. 네 관점 Agent는 실행 뒤 Supervisor로 돌아온다. `add_conditional_edges`를 통해 현재 누락·근거 부족·에러에 따른 대상 선택을 구현한다. 특정 관점만 부족한 입력 두 종류에서 경로가 달라지는 테스트, 하나의 관점만 재작업하는 테스트, 상한에서 실패 종료하는 테스트를 먼저 작성한다. 종합·보고서 작성은 충분성 판정 후만 가능하게 한다.

## State/기술 조사 작업

제어·결과·외부 로그 경계를 분리하고 trace_id, 상태, 관점별 시도 횟수, 마지막 오류, 품질 verdict를 정의한다. 결과 ID가 재작업 병합에서 소실되지 않도록 reducer를 검증한다. 기술 Agent는 기존 기술·TRL 결과를 adapter로 반환하며 보완 질의를 실제 RAG에 반영한다. 메모리 checkpoint와 프로세스 재시작 영속 복구의 구현 범위를 명시한다.

## 시장/이해관계자/도메인 작업

기존 검색·프롬프트를 유지하면서 공통 작업 입력·출력 계약을 수용한다. 부족 사유에 따른 추가 질의를 구현하고 success/insufficient/error를 구분한다. 각 결과에 주장·근거·공개 정보 부족 항목을 연결한다. 다른 관점 Agent를 직접 호출하지 않는다. 담당 관점의 첫 실패→재작업→성공 테스트와 영구 실패 사례를 제공한다.

## 품질 평가/보고서 작업

보고서 생성 뒤 네 기준을 평가하는 노드를 분리한다. 규칙 검사와 LLM Judge 결과를 구조화하고 내용 관련 실패를 표현 수정/근거 재조사로 구분한다. Judge 자체의 파싱 실패를 pass로 처리하지 않는다. failed→rewrite→pass, failed→research→재평가, 상한 종료를 테스트한다. 본문 주장-근거 연결과 10쪽 제한을 반영해 기존 확장 프롬프트를 조정한다.

## 추적/제출 작업

결정 사유와 trace_id를 LangSmith 및 외부 로그에 남긴다. 실제 Graph trace와 OpenAI SDK 호출을 확인한다. 정상·재작업·품질 Loop 기록에 commit과 산출물 경로를 연결한다. 최종 PDF 내용·쪽수·레이아웃을 검사하고 README와 Contributors를 실제 구현에 맞춘다. 제출용 ZIP의 캡처·PDF·Git 링크가 동일 코드 버전을 가리키는지 확인한다.
