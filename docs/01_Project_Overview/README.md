# 과제 요구사항과 현재 구현 분석

## 목적과 범위

DeepSeek-V2 MLA(SW)와 ITME(HW)를 데이터센터·클라우드 LLM 서빙 환경에서 기술 성숙도, 시장성, 이해관계자, 도메인 적용의 네 관점으로 평가한다. 기술 선정은 기존 Human 기반 방식을 유지한다. 특정 기술을 추천하거나 서로 다른 환경의 수치를 단순 우열 비교하지 않는다.

이번 과제의 새로운 핵심은 동적 Agent 조정, State 설계, 생성 후 품질 평가, 실행 추적이다. 기존 RAG 검색과 보고서 기능을 바탕으로 조정 계층을 추가한다.

## 기존 실행 흐름

`app.py`가 논문 다운로드→청킹→ChromaDB 색인을 수행한다. `graph.py`는 기술 선정→기술 조사→고정된 세 관점 병렬 평가→종합→검증→보고서 생성으로 연결한다. 검증 실패 시 항상 기술 조사로 돌아가 모든 관점을 재실행한다. 보고서는 MD·HTML·JSON·PDF로 저장하는 코드가 있다.

| 파일 | 현재 역할 | 이번 과제에서 필요한 변화 |
|---|---|---|
| `graph.py` | 고정 Fan-out/Fan-in, 생성 전 검증 분기 | Supervisor 노드와 State 기반 라우팅, 생성 후 품질 평가 Loop |
| `state.py` | 관점별 dict, references reducer, 오류 누적 | 구조화 결정·근거 판정·상태·시도 횟수·상관 키·유한 종료 |
| `agents/technical_research.py` | 논문 RAG, 기술 및 TRL 분석 | 재작업 사유·추가 질의 입력 수용. 현재 `_state`를 사용하지 않음 |
| `agents/market_evaluation.py` | 웹 검색·시장성 분석 | 해당 관점 재작업 피드백과 근거 다양성 결과 반환 |
| `agents/stakeholder_evaluation.py` | 웹 검색·이해관계자 분석 | 해당 관점 재작업 피드백과 근거 다양성 결과 반환 |
| `agents/domain_evaluation.py` | 기술별 도메인 질의·논문 RAG | State의 보완 요청 수용; 현재 정해진 기준 질의만 사용 |
| `agents/synthesis.py` | 종합·규칙 Judge·보고서 작성 | 생성 후 품질 판정 분리, 주장별 출처 연결 보존, 분량 축약 |
| `evidence.py` | 근거 ID·출처·기술별 문맥 예산 | 재작업 후에도 인용 ID 일관성, 출처 유형·독립성 검증 |
| `llm.py` | OpenAI SDK 직접 호출 | LLM 호출 trace 계측, Judge 출력 스키마 검증 |
| `evaluate.py` | 10문항 Hit@K/MRR 평가 코드 | 실제 실행·지표 저장; 보고서 품질 평가와 별도로 관리 |
| `app.py` | 실행 및 산출물 저장 | trace/run/thread 연결, 품질 실패 상태 표시, PDF 쪽수 확인 |

## 평가표에 맞춘 우선순위

| 채점 항목 | 배점 | 현재 확인한 상태 | 구현 완료 증거 |
|---|---:|---|---|
| 패턴 적용 정합성 | 20 | 고정 병렬 흐름으로 미충족 | Supervisor 조건부 라우팅·Agent 복귀·근거 판정·특정 관점 재작업 |
| 동적 동작 실증 | 20 | LangSmith 설정·캡처 미확인 | 서로 다른 State의 라우팅, 시장성 재조사 trace 등 |
| State Schema | 20 | references/errors reducer는 있음; 나머지 설계 부족 | 7항목 설명과 실제 필드·저장·복구 코드 |
| 품질 평가 노드 | 15 | `report_generation → END`; 생성 후 노드 없음 | 네 항목 판정과 실패 후 재작성/재조사 Loop |
| 구조·모듈 분리 | 5 | 기존 역할별 모듈 있음 | 조정 계층·품질 판정·관점 Agent 분리 |
| 실행 재현성 | 10 | 이번 세션 실서비스 실행 미검증 | 정상·재작업·상한 종료 실행 및 동일 환경 기록 |
| 보고서 | 10 | 목차와 export 코드 있음 | 실제 생성 PDF ≤10쪽, SUMMARY·REFERENCE 및 사실 검수 |

총점을 예측하지 않는다. 기존 코드로 충족되는 항목과 이번 과제에서 새로 구현할 항목을 구분한다.

## 특히 놓치기 쉬운 부분

1. `retry_targets`가 있어도 지금 Graph는 이를 라우팅에 사용하지 않는다. 필드를 기록하는 것만으로 동적 재작업이 되지 않는다.
2. 기존 Judge는 분석 dict와 ID 존재를 검사한다. 출처가 주장 내용을 실제로 뒷받침하는지, 보고서가 중립적인지까지 판단하지 않는다.
3. 현재 보고서 생성 프롬프트가 본문 근거 ID를 숨긴다. 최종 본문 주장과 출처의 연결을 유지하도록 각주/ID 또는 별도 주장 매핑이 필요하다.
4. 현재 프롬프트는 여러 절을 각각 700자 이상으로 확장한다. 새 과제의 10쪽 제한과 충돌할 수 있어 실제 PDF 쪽수를 기준으로 축약한다.
5. `.env.example`는 README에서 안내하지만 현재 팀 main에 파일이 없다. 실행 담당자가 비밀값 없는 샘플 파일을 추가해야 한다.
6. 현재 `config.py`가 import 시 API key를 요구한다. 오프라인 제어 흐름 테스트는 SDK 호출과 클라이언트 초기화를 분리하거나 mock 주입이 필요하다.
7. `FAST_MODE=True`는 현재 재시도 0회다. 정상 실행만 보면 재작업 기능을 입증할 수 없다.
