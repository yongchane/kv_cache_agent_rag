# 보고서와 제출 증빙 설계

## 제출물 3종

1. GitHub branch 링크와 README — 패턴·선정 이유·동적 동작·State 7항목·구조도·실행법·실제 Contributors.
2. LangSmith 실행 캡처 — 긴 경로는 `tracing-1.png`, `tracing-2.png`처럼 순서 부여. 실제 State 판단과 재작업 경로를 확인할 수 있어야 한다.
3. KV cache 기술 평가 보고서 PDF — 이전 구성 유지, 최대 10쪽. SUMMARY와 REFERENCE 필수.

최종 파일명: `Agent_{캠퍼스}_{X반}_{이름1+이름2+...}.zip`. 캠퍼스와 이름 표기는 반별 제출 규칙을 확인해 채운다. 지침의 반별 Slack thread에 Git Link+PNG+PDF를 제출한다. 이 문서는 제출 준비안이며 자동 업로드를 수행하지 않는다.

## 10쪽 보고서 구성안

다음은 페이지 배분 목표다. 실제 PDF 렌더링 후 조정한다. 기술 평가 보고서를 개발 후기 보고서로 바꾸지 않는다. 패턴·State의 상세 설명은 README에 두고, 보고서는 기술의 근거와 네 관점 평가에 집중한다.

| 쪽 | 내용 | 필요한 증거 |

| 1 | SUMMARY·평가 목적·범위 | 중립적인 결론과 추가 검증 과제 |

출처가 많으면 본문을 더 줄여 REFERENCE에 2쪽을 배정해도 된다. 본문 수치를 먼저 지우기보다 중복 설명을 줄인다. 쪽수를 맞추기 위해 근거 글자를 읽기 어렵게 줄이지 않는다.

## 실행별 증빙

| 실행 | 보여줄 내용 | 필요한 캡처·기록 |
|---|---|---|
| 정상 | 충분성 판단 후 최종 작성·품질 통과 | 전체 Graph trace, verdict, 최종 PDF |
| 재조사 | 특정 관점의 근거 부족→해당 Agent 재호출 | 분기 전 상태·decision reason·재호출·추가 근거 |
| 보고서 품질 보완 | 생성 후 quality fail→rewrite/research→재평가 | 최초 fail 이유와 수정 후 verdict |
| 종료 상한 | 끝없이 retry하지 않고 failure 종료 | 테스트 결과와 종료 상태; 가능하면 실제 trace |

지침은 여러 실제 실행 개수를 고정하지 않는다. 위 사례는 동적 동작과 Loop를 입증하기 위한 권장 증빙이다. 검증용 부족 입력을 사용했다면 이를 명시한다.

권장 run별 manifest: `trace_id`, `thread_id`, `langsmith_run_id/url`, `git_commit`, `pattern`, 모델·패키지 버전, FAST_MODE, 시작/종료 시각, 실행 상태, 테스트/mock 여부, 보고서·verdict·캡처 파일 경로. 값은 실제 실행 때 채운다.

## 제출 직전 확인

- [ ] 캡처는 제출 브랜치의 최신 코드 실행 결과다.
- [ ] Graph 그림만 제출하지 않고 실제 LangSmith trace가 있다.
- [ ] 재작업 선택 이유와 대상이 식별된다.
- [ ] Judge가 보고서 생성 뒤 실행되고 실패 Loop가 보인다.
- [ ] 네 관점의 주요 주장에 실제 출처가 연결된다.
- [ ] 수치의 단위·비교 기준·실험 환경을 원문과 대조했다.
- [ ] TRL을 논문 발표 사실만으로 확정하지 않았다.
- [ ] 직접 자료와 관련 생태계·기업 홍보 자료를 구분했다.
- [ ] PDF 실제 페이지 수가 10 이하이며 잘린 표·글자가 없다.
- [ ] README 기술 스택·State·그래프가 최신 코드와 같다.
- [ ] Contributors는 실제 개인별 작업이며 PM/PL 역할명이 없다.
- [ ] 신규 환경 실행 명령과 필요한 키 이름을 안내했다.
- [ ] ZIP에 `.env`, API key, 로컬 DB·의존성 폴더가 포함되지 않는다.

기존 9월 보고서의 기술 평가 내용과 지표는 검수 없이 복사하지 않는다. 최신 실행 전에 목표 수치를 실제 성과로 기재하지 않는다.
